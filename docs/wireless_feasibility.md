# RepAI Wireless Feasibility: SparkFun MyoWare 2.0 Wireless Shield

Date: 2026-07-22

This note evaluates whether one SparkFun MyoWare 2.0 Wireless Shield can send the existing MyoWare 2.0 Muscle Sensor signal directly to a Mac for RepAI recording. This is a research-only feasibility pass. No hardware has been physically tested yet.

## Verdict

Direct Wireless Shield-to-Mac reception looks technically feasible for RepAI's current ENV signal workflow.

The official Wireless Shield firmware exposes a custom BLE service and a notify/read characteristic. A Mac can act as the BLE central through CoreBluetooth, and a Python receiver using Bleak should be able to scan for the service, connect, and subscribe to notifications.

The main caveat is timing. The official BLE payload is only the sensor value string. It does not include a device timestamp, so a direct Mac receiver would preserve RepAI's current CSV shape by writing:

```csv
time_ms,emg_value
0,1234
10,1240
```

but `time_ms` would be generated by the Mac at receive time, not by the Wireless Shield's ESP32 unless the peripheral firmware is changed to include timestamps.

For repetition detection on the MyoWare ENV output, this should be good enough if the receiver achieves a stable tens-of-Hz to ~100 Hz stream. It is not a good assumption for raw EMG fidelity without hardware timing tests.

## Payload Format

The official `MyoWareBLEPeripheral` example creates:

```cpp
BLEStringCharacteristic(..., BLERead | BLENotify, 128)
```

In its connected loop, it reads the selected MyoWare output and writes it as a string:

```cpp
String(myoware.readSensorOutput(outputType))
```

Default settings in the example:

- `outputType = MyoWare::ENVELOPE`
- `myoware.setConvertOutput(false)`
- ENV pin: `A3`
- RAW pin: `A4`
- REF pin: `A5`
- ADC resolution default in the library: 12-bit
- ADC reference voltage default in the library: 3.3 V

With conversion disabled, the default transmitted value is an ASCII decimal representation of the raw ADC-style ENV reading. If RAW is selected, the library returns `rawValue - refValue`. If conversion is enabled in firmware, the string represents the converted millivolt value instead.

## Sampling And Transmission Rate

The current official Wireless Shield peripheral example does not set a fixed sample period and does not include an explicit `delay()` in the send loop. It writes the characteristic as fast as the loop, serial debug output, BLE stack, and connection interval allow.

Practical implication for RepAI:

- There is no documented fixed default rate to rely on.
- The achieved notification/read rate must be measured with the real shield.
- If the stream is too fast, jittery, or unreliable, adding a small peripheral delay such as 10 ms would target ~100 Hz.
- RepAI's current saved real CSV example is effectively 10 ms spaced, or ~100 Hz.
- The MyoWare ENV output is already an envelope signal, so a stable rate well below raw EMG rates can still be useful for rep detection.

Older SparkFun BLE example material for a RedBoard Artemis path maps a 10-bit analog reading to one byte and uses a 10 ms delay. That is useful historical context, but the official MyoWare 2.0 Wireless Shield library example currently uses the custom MyoWare UUIDs above and a string characteristic.

## Direct Mac Central Feasibility

A direct Mac receiver is reasonable because:

- The Wireless Shield is an ESP32-WROOM BLE peripheral.
- It advertises a custom service UUID.
- The sensor characteristic is readable and notifiable.
- macOS can act as a BLE central through CoreBluetooth.
- Bleak supports macOS through its CoreBluetooth backend and exposes `start_notify()`.

SparkFun demonstrates an ESP32 central receiver, but nothing in the BLE design requires that the central be SparkFun's ESP32 board. The ESP32 central is the officially documented Arduino-friendly receiver path, not a technical requirement for BLE itself.

## RepAI CSV Compatibility

Direct Mac reception can preserve the current RepAI CSV columns:

```csv
time_ms,emg_value
```

Recommended receiver behavior:

- Start a monotonic clock when recording begins.
- On each BLE notification, decode the ASCII value.
- Write elapsed host time in milliseconds as `time_ms`.
- Write the parsed numeric payload as `emg_value`.

This keeps detector compatibility because `python/detect_reps.py` already reads `time_ms` and accepts `emg_value`.

Limitation: host receive timestamps include BLE scheduling jitter. They are not the same as microcontroller sample timestamps.

## Data Rate For Current ENV Workflow

For current RepAI ENV-based repetition detection, the expected data rate is likely sufficient if physical testing shows a stable notification stream around tens of Hz or better.

Why:

- The current workflow analyzes the smoothed envelope, not high-frequency raw EMG.
- The detector uses threshold crossings over rep-scale time windows.
- Existing real CSV samples are roughly 10 ms apart.

What would not be safe to assume yet:

- Reliable 100 Hz under all macOS/BLE conditions.
- Raw EMG quality over the default string-notification firmware.
- Low-jitter timing suitable for spectral analysis or high-resolution fatigue metrics.

## macOS Concerns

macOS/Bleak concerns to plan for:

- Bluetooth permission must be granted to the app running Python, such as Terminal, iTerm, VS Code, or a packaged app.
- Packaged macOS apps need an `NSBluetoothAlwaysUsageDescription` entry in `Info.plist`.
- If Bluetooth permission is denied, Bleak can raise `BleakBluetoothNotAvailableError`; the user must re-enable access in System Settings.
- macOS identifies BLE devices by CoreBluetooth UUIDs, not stable Bluetooth MAC addresses.
- On macOS 12.0 through 12.2, Bleak scanning may require passing a non-empty `service_uuids` filter.
- Bleak pairing is not implemented on macOS, but this characteristic should not need pairing/authentication.
- SparkFun's example notes ArduinoBLE reconnection limitations and recommends reset order if the BLE connection fails.
- BLE reliability should be tested in the gym environment because distance, body position, interference, laptop sleep, and multiple peripherals can affect streaming.
- The Wireless Shield uses a CH340 USB-to-serial converter for programming, so a CH340 driver may be needed depending on the Mac setup.

Safety concern:

- SparkFun warns not to charge or program the Wireless Shield while it is stacked on the MyoWare sensor and attached to a person. Use battery power for body-connected recordings.

## Minimum Purchase Lists

### A. Direct Wireless Shield To Mac

Assuming the existing MyoWare 2.0 Muscle Sensor is already owned:

- 1x SparkFun MyoWare 2.0 Wireless Shield, DEV-23387
- EMG electrode pads, if not already available
- USB-C cable for charging and programming the Wireless Shield
- Mac with BLE support

No ESP32 receiver board is required for this path.

Software needed:

- Arduino IDE or equivalent only if firmware changes are needed
- MyoWare Arduino Library if flashing the official examples
- Python BLE library such as Bleak for the future experimental receiver

### B. Wireless Shield To ESP32 Receiver To Mac

Assuming the existing MyoWare 2.0 Muscle Sensor is already owned:

- 1x SparkFun MyoWare 2.0 Wireless Shield, DEV-23387
- 1x BLE-capable Arduino-compatible central board, such as the SparkFun IoT RedBoard ESP32 used in SparkFun's guide
- USB cable for the ESP32 central receiver
- USB-C cable for charging and programming the Wireless Shield, if not already available
- EMG electrode pads, if not already available

Software needed:

- Arduino IDE
- ESP32 board definitions for the central board
- ArduinoBLE library
- MyoWare Arduino Library
- Existing RepAI serial recorder can remain conceptually similar if the ESP32 central prints `time_ms,emg_value`, but the official central example currently prints sensor values and would need a small serial-format sketch change before it exactly matches RepAI's CSV parser.

## Recommendation

Buy the Wireless Shield first if the goal is to prove feasibility with the least hardware.

Direct-to-Mac is the simpler RepAI architecture if Bleak proves reliable:

- fewer boards
- no extra serial bridge
- direct CSV writing from Python
- easier metadata prompts and file naming later

Buy the ESP32 central receiver only if one of these turns out to be true:

- macOS BLE permissions/reliability are painful
- direct Bleak notification timing is too jittery
- you want a SparkFun-documented Arduino-to-Arduino setup first
- you eventually need multiple Wireless Shields and prefer embedded aggregation

## Uncertainties Requiring Physical Testing

- Whether the purchased shield ships with the current MyoWare BLE peripheral firmware and the UUIDs listed above.
- Actual notification frequency on the Mac with Bleak.
- Notification jitter and dropped-packet behavior during movement.
- Whether serial debug output in the firmware affects practical BLE throughput.
- Whether host-generated timestamps are stable enough for RepAI's comparison summaries.
- Battery runtime during a full workout-style session.
- Signal quality difference between wired Arduino recording and wireless battery-powered recording.
- macOS permission behavior for the exact Python host used locally.
- Whether one shield stays connected reliably after repeated start/stop recording sessions.
